# MathDemo — учебный проект на C++ с CMake

## Структура проекта

```
MathDemo/
├── CMakeLists.txt       ← корневой файл сборки
├── main.cpp             ← точка входа программы
└── math/                ← подпапка-библиотека
    ├── CMakeLists.txt   ← файл сборки библиотеки
    ├── include/         ← заголовочные файлы (.hpp)
    │   ├── multiply.hpp
    │   ├── divide.hpp
    │   └── power.hpp
    └── src/             ← файлы реализации (.cpp)
        ├── multiply.cpp
        ├── divide.cpp
        └── power.cpp
```

## Что такое CMake и зачем он нужен

### Этапы компиляции

Компиляция одного `.cpp` файла состоит из четырёх последовательных шагов:

| Шаг | Что происходит | Вход → Выход |
|-----|---------------|--------------|
| **1. Препроцессинг** | Препроцессор обрабатывает директивы `#include`, `#define`, `#pragma once`. Вместо `#include <multiply.hpp>` буквально вставляется текст файла `multiply.hpp`. | `.cpp` → расширенный `.cpp` |
| **2. Компиляция** | Компилятор переводит C++ код в **ассемблерный код** — текстовое представление инструкций конкретного процессора. | расширенный `.cpp` → `.s` |
| **3. Ассемблирование** | Ассемблер переводит ассемблерный код в **объектный файл** — двоичный файл с машинным кодом. | `.s` → `.o` |
| **4. Линковка** | Линкер объединяет все `.o` файлы и библиотеки, разрешает все вызовы функций (каждый вызов получает реальный адрес в памяти) и создаёт итоговый исполняемый файл. | несколько `.o` + `.a` → `demo` |

**Объектный файл** (`.o`) — это скомпилированный код одного `.cpp` файла. Он уже содержит машинные инструкции, но пока не знает, где в памяти будут находиться функции из других файлов: вместо реальных адресов там стоят заглушки. Линкер на последнем шаге заполняет эти заглушки, «склеивая» файлы вместе.

Статическая библиотека `.a` — это просто **архив** из нескольких `.o` файлов, упакованных утилитой `ar`.

### Проблема: сборка руками

Для нашего проекта команды компилятора выглядели бы так:

```bash
# -c         : только компилировать, без линковки; результат — объектный файл .o
# -I <путь>  : добавить директорию в пути поиска заголовочных файлов
# -o <файл>  : имя выходного файла
g++ -c math/src/multiply.cpp -I math/include -o multiply.o
g++ -c math/src/power.cpp    -I math/include -o power.o
g++ -c math/src/divide.cpp   -I math/include -o divide.o

# ar    : утилита архивации объектных файлов в статическую библиотеку
# r     : вставить/заменить файлы в архиве
# c     : создать архив, если его нет
# s     : добавить индекс символов (ускоряет линковку)
ar rcs libmath.a multiply.o power.o divide.o

# -L <путь>  : добавить директорию в пути поиска библиотек
# -l <имя>   : слинковать с библиотекой lib<имя>.a
g++ main.cpp -I math/include -L. -lmath -o demo
```

Пока файлов три — терпимо. Но представьте проект из 200 файлов. Тогда:

- нужно помнить **точный порядок** компиляции;
- нужно вручную отслеживать, **какой файл изменился**, чтобы перекомпилировать только его;
- при ошибке в одной команде всё ломается, и непонятно где.

Особенно опасна вторая проблема: **если забыть перекомпилировать нужный `.cpp` файл**, в библиотеку попадёт старый объектный файл со старой логикой. Программа соберётся без ошибок, запустится — но будет работать по старому коду. В редакторе вы видите новые изменения, а в памяти выполняется что-то другое. Такие баги крайне сложно найти.

### Что такое Makefile

`Makefile` — это первое решение проблемы. Он описывает **граф зависимостей**: «чтобы собрать `demo`, нужны `libmath.a` и `main.o`; чтобы собрать `libmath.a`, нужны `multiply.o`, `power.o`, `divide.o`». Утилита `make` читает этот граф и **запускает нужные команды компилятора** в правильном порядке — компилятор уже сам разбирается, какие файлы изменились с прошлого запуска и нуждаются в пересборке.

Это решает проблему «забыл перекомпилировать», но создаёт новую: `Makefile` нужно писать вручную, и он **привязан к конкретной ОС и компилятору**. На Linux — один синтаксис и флаги, на Windows с MSVC — совсем другие.

### Что такое CMake

CMake — это **система сборки над системой сборки**. Вы пишете `CMakeLists.txt` один раз на платформо-независимом языке CMake, а CMake сам генерирует нужный `Makefile` (на Linux), проект для Visual Studio (на Windows), или `.ninja` файл (для сборщика Ninja). Итого:

| Задача | Решение |
|--------|---------|
| Не забыть перекомпилировать изменившиеся файлы | CMake → Make/Ninja отслеживает зависимости автоматически |
| Переносимость между ОС и компиляторами | Один `CMakeLists.txt` для всех платформ |
| Управление зависимостями между модулями | `target_link_libraries` + граф целей |

CMake **не компилирует** код сам. Он читает `CMakeLists.txt` и генерирует файлы для реального компилятора, который уже и делает работу.

## Ключевые концепции

### `#pragma once`

Директива в начале каждого `.hpp` файла, которая запрещает компилятору включать этот файл более одного раза в рамках одной единицы компиляции. Без неё при двойном `#include` получились бы ошибки «already defined».

### Разделение на `.hpp` и `.cpp`

| Файл | Что содержит |
|------|-------------|
| `.hpp` (заголовок) | **объявление** функции — её имя, параметры и тип возврата |
| `.cpp` (реализация) | **определение** функции — сам код, что она делает |

Такое разделение позволяет другим файлам знать *как вызвать* функцию (через `.hpp`), не видя её реализации.

### Зачем нужны статические библиотеки

**Статическая библиотека** (`.a` на Linux, `.lib` на Windows) — это архив из нескольких скомпилированных объектных файлов. В нашем проекте `libmath.a` содержит `multiply.o`, `power.o` и `divide.o`.

Программисты выносят код в библиотеки по нескольким причинам:

1. **Повторное использование.** Одну и ту же `libmath.a` можно подключить к десяткам разных исполняемых файлов, не копируя исходники.
2. **Изоляция.** Каждая библиотека компилируется независимо. Если вы изменили только `multiply.cpp`, пересобирается только `multiply.o`, а затем переупаковывается `libmath.a` — остальные файлы трогать не нужно.
3. **Параллельная сборка.** Независимые библиотеки CMake может компилировать одновременно на разных ядрах процессора.

### Перекомпиляция: что происходит при изменении

Когда вы меняете один файл в библиотеке, CMake/Make выполняет **минимально необходимый** набор шагов:

```
изменили multiply.cpp
       ↓
перекомпилировать multiply.cpp → multiply.o
       ↓
переупаковать libmath.a (заменить старый multiply.o на новый)
       ↓
перелинковать demo (т.к. libmath.a изменилась)
```

`power.o` и `divide.o` при этом не трогаются — их исходники не менялись.

Важно понимать **транзитивность**: если `libmath.a` пересобралась, то `demo` **обязан** перелинковаться заново, даже если `main.cpp` не менялся. CMake отслеживает эту цепочку автоматически: `demo` зависит от `libmath.a`, значит при любом изменении библиотеки исполняемый файл пересобирается. Именно это гарантирует, что в запущенной программе всегда находится актуальная версия кода.

### `add_subdirectory`

[Документация](https://cmake.org/cmake/help/latest/command/add_subdirectory.html)

Команда `add_subdirectory(math)` в корневом `CMakeLists.txt` делает три вещи:

1. **Находит** файл `math/CMakeLists.txt` и выполняет все команды из него.
2. **Регистрирует** все цели (targets), объявленные внутри, — в нашем случае библиотеку `math` — как известные в корневом контексте сборки.
3. **Сохраняет** переменную `CMAKE_CURRENT_SOURCE_DIR` внутри подпапки, чтобы пути вычислялись относительно `math/`, а не корня.

После `add_subdirectory(math)` можно писать `target_link_libraries(demo PRIVATE math)` — CMake уже знает, что `math` это цель из подпапки, и правильно выстроит порядок сборки: сначала `libmath.a`, потом `demo`.

Технически подпапка может иметь **собственный граф зависимостей**, свои флаги компилятора и свои пути — она полностью самостоятельна. Корень лишь «импортирует» её результат.

### Библиотека и `target_link_libraries`

[Документация](https://cmake.org/cmake/help/latest/command/target_link_libraries.html)

Папка `math/` собирается не в исполняемый файл, а в **библиотеку** (`add_library`). `target_link_libraries(demo PRIVATE math)` говорит линкеру: «при сборке `demo` возьми весь код из `libmath.a` и включи его в исполняемый файл».

Ключевое слово `PRIVATE` означает, что зависимость от `math` касается только `demo` и не «протекает» дальше по графу зависимостей.

### `target_include_directories` с `SYSTEM PUBLIC`

[Документация](https://cmake.org/cmake/help/latest/command/target_include_directories.html)

Чтобы в `main.cpp` можно было писать `#include <multiply.hpp>` (через угловые скобки, как системный заголовок), папка `math/include/` добавляется в системные пути поиска:

- `SYSTEM` — помечает директорию как системную: компилятор не будет выдавать предупреждения на файлы из неё, и работает синтаксис `#include <...>`.
- `PUBLIC` — путь наследуют **все цели**, которые линкуются с `math`. Именно поэтому в `main.cpp` не нужно отдельно прописывать путь до заголовков — он приходит транзитивно через `target_link_libraries(demo PRIVATE math)`.

## Сборка и запуск

```bash
# создаём папку для файлов сборки (чтобы не засорять исходники)
cmake -S . -B build

# компилируем
cmake --build build

# запускаем
./build/demo
```

Ожидаемый вывод:

```
3 * 4 = 12
3 / 4 = 0.75
3^3 = 27
```
